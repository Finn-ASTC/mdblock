# docs/

三类文档，按「谁该读」分开：

| 目录 | 内容 | 读者 |
|---|---|---|
| `design/` | 设计 spec（已批准的架构决策、参数面、明确不做的东西） | 想理解**为什么这样设计**的人 |
| `orch/` | 模块接口契约 + 6 份模块任务书 + 编排实测报告 + 一次盲评裁决原文 | 想知道**这个项目是怎么造出来的**的人 |

## 关于 `orch/`

这个仓库的实现过程是一次「异构多 agent 编排」的实地测试：项目被切成 6 个文件不相交的模块，
每个模块一条 git 分支 + 一个独立 worktree + 指定一个终端 agent（四种不同的 CLI agent），
控制方（一个人）负责冻结契约、按轮调度、独立验收、合并整理。

- `CONTRACT.md` —— **在扇出之前冻结的模块接口契约**，是所有实现者的唯一规范；
  文件末尾的「修订记录 A-1…A-5」记录了实现过程中发现并修正的每一条缺陷及其证据
- `briefs/` —— 发给每个 agent 的任务书原文（测试它们的原始输入）
- `report.md` —— 实测数据：轮次耗时、逐模块吞吐、9 条工具缺陷、验收层次分析、可复用做法
- `judge-verdict.md` —— 一次**盲评**的完整输出：两份实现匿名化后交给第三个 agent 评审，
  它自己造夹具、跑 44 条判据 + 37 例对拍，并用真实样式表在 Chromium 里实测

文档里出现的 `<repo>/` 与 `.orchestrator/` 是控制方的临时工作目录（轮次信封、验收探针、
盲评材料），**没有随仓库发布**。`docs/orch/briefs/judge-m4.md` 引用它们时按此理解即可。

`report.md` 里保留了对具体工具与失败模式的点名 —— 那是实测结论的一部分，不是为了推荐或贬低任何工具。
